# Urspace session grants

Status: protocol v4 design contract.

Urspace invitations are bearer enrollment credentials. A browser presents an
invitation once to create an admitted session. Successful admission returns a
host-signed session grant that can reconnect that session without retaining the
invitation capability.

A session grant is not a bearer credential. It is bound to a browser session
public key, and the host accepts it only together with a fresh proof made by the
corresponding private key. Cloud bootstrap infrastructure may store and return
the signed grant, but cannot use it to enter the private site.

## Security invariants

- The host is the only authority that can admit, reconnect, kick, or revoke a
  browser session.
- Invitation capabilities are used only for initial admission and are never
  embedded in a session grant.
- A copied session grant is unusable without its browser session private key.
- A copied proof is unusable on another connection or after its challenge has
  been consumed.
- Proofs are bound to the exact host, site, ALPN, signed grant, and current Iroh
  endpoint identity.
- Invite rotation closes only new admissions. Previously admitted sessions may
  reconnect until kicked, revoked, forgotten by the host, or rejected by an
  explicitly configured session-expiry policy.
- Kicks and revocations are stateful and take effect immediately. Signed grants
  never override host state.
- The hosted application never receives the invitation capability or browser
  session private key.
- Unknown versions, algorithms, fields, and non-canonical encodings fail closed.

## Identities

- `host_id`: the Ed25519 public key that identifies the Iroh site endpoint and
  signs invitations and session grants.
- `session_id`: 128 random bits allocated by the host for one admitted browser.
- `session_key`: an Ed25519 key generated by the browser for admission
  continuity. It is distinct from the Iroh transport endpoint key.
- `endpoint_id`: the browser's current Iroh transport identity. It may change on
  every cold reconnect.

Separating `session_key` from `endpoint_id` allows a browser to create a fresh
Iroh endpoint after worker eviction while the host continues to recognize the
same admitted session.

## Signed grant

The v1 grant payload is a fixed, versioned structure:

```text
SessionGrantV1 {
  version: 1,
  host_id: [u8; 32],
  site_id: string,
  bootstrap_origin: string,
  endpoint_ticket: string,
  invite_id: uuid,
  session_id: uuid,
  session_public_key: [u8; 32],
  issued_at_unix: i64,
  expires_at_unix: i64,
  authorization_epoch: u64,
  entry_path: string,
}
```

The envelope contains the payload plus the host public key and an Ed25519
signature over the domain separator `urspace-session-grant-v1`, followed by the
canonical serialized payload. The signer must equal both `host_id` and the Iroh
identity in `endpoint_ticket`. The bootstrap origin must derive the exact
capability-isolated site origin for `site_id`.

The grant contains public routing and authorization assertions but no bearer
secret. Implementations must still avoid logging it because it identifies a
private browsing relationship. Foreground sharing keeps authorization state in
memory. Named service mode journals the host-side registry and pins the relay
address embedded in grants, allowing admitted sessions to survive a host process
restart without relaxing exact endpoint-ticket validation. Host kick, invite
revocation, or browser departure remains authoritative.

## Admission handshake

All messages use the `urspace-site/4` ALPN and length-bounded canonical frames.

```text
browser -> host  Admit { invite_id, capability, session_public_key }
host    -> browser  Challenge { nonce, challenge_id, expires_at_unix }
browser -> host  Proof { challenge_id, signature }
host    -> browser  Granted { session_grant }
```

The host validates the invitation before sending a challenge but consumes an
admission slot only after the proof succeeds. The admission proof signs the
same transcript described below. A failed, expired, or abandoned challenge
does not consume a session slot.

## Reconnect handshake

```text
browser -> host  Resume { session_grant }
host    -> browser  Challenge { nonce, challenge_id, expires_at_unix }
browser -> host  Proof { challenge_id, signature }
host    -> browser  Granted { rotated_session_grant }
```

Before challenging, the host verifies the grant signature, exact audience,
expiry, and current session record. After receiving the proof, it rechecks the
record atomically and replaces any older live connection for that session.

The browser signs canonical bytes containing:

```text
SessionProofV1 {
  version: 1,
  purpose: admit | resume,
  host_id: [u8; 32],
  site_id: [u8; 32],
  alpn: "urspace-site/4",
  session_id: uuid,
  session_grant_hash: [u8; 32],
  endpoint_id: [u8; 32],
  challenge_id: uuid,
  nonce: [u8; 32],
  expires_at_unix: i64,
}
```

Admission uses an all-zero grant hash because no grant exists yet. The host
creates every nonce and accepts each challenge exactly once. The signature is
over the domain separator `urspace-session-proof-v1` followed by the canonical
proof bytes.

## Host state

Immediate revocation requires a small stateful registry:

```text
session_id -> {
  invite_id,
  session_public_key,
  authorization_epoch,
  access_label?,
  active | kicked | revoked,
  current_endpoint_id,
}
```

The signed `authorization_epoch` must equal the registry value. Kicking a
session marks it kicked and closes its current connection. Revoking an invite
revokes all sessions admitted by it. A host that does not persist the registry
must reject all old grants after restart; it must never reconstruct authority
from a grant alone. Named service mode persists registry mutations as a private
append-only journal. It writes and syncs the event before changing live
authorization state, restores only complete events, and never records capability
plaintext or a browser private key.

An optional access label is inherited from the invitation and remains host-side
administrative metadata. It helps an owner find a device in `service sessions`,
but it is neither signed into the browser grant nor accepted as identity proof.

## Browser and Worker recovery

The signed grant and session private key are separate recovery factors.

- The service worker holds both factors only in memory while it owns the active
  Iroh client.
- For navigation responses, the worker injects a nonce-authorized first script
  containing an encoded memory handoff. That script captures the handoff in a
  closure and removes its element before application scripts run.
- The script proactively returns the handoff to the exact-origin service worker
  on `beforeunload`, `pagehide`, and transition to hidden. It can also answer a
  trusted service-worker recovery request through a transferred message port.
- A restarted service worker verifies the handoff structure and exact origin,
  creates a fresh Iroh endpoint, then proves possession of the session key to the
  host. A rotated grant replaces the previous grant after success.
- Normal refresh and idle worker eviction recover automatically. Closing all
  controlled pages, a discarded page, or a browser process restart destroys the
  memory-only factors and requires reopening an invitation.

The Cloudflare Worker serves generic immutable bootstrap code only. It does not
store either recovery factor, terminate Iroh, or carry application traffic.

## Native managed-device recovery

`urspace connect` uses the same proof-bound grant but stores its device key in a
private local file rather than handing it to the browser. A fresh client process
can therefore resume after all pages and the previous process are gone. It
verifies the grant locally, creates a fresh Iroh transport endpoint, answers the
host's fresh challenge, and exposes only a random `*.localhost` gateway to the
browser. The Cloudflare bootstrap and service worker do not participate.

## Required negative tests

- bit-flipped payload and signature
- signer, endpoint-ticket, site, and origin substitution
- grant presented without its private key
- proof replay and duplicate challenge consumption
- proof copied to a different Iroh endpoint
- proof or grant expiry boundary
- wrong purpose, ALPN, session, grant hash, or authorization epoch
- invitation rotation before and after admission
- concurrent final admission against the last available slot
- kick and invite revocation during a challenge
- host restart with missing session state
- v3/v4 downgrade and cross-version decoding
- oversized, truncated, non-canonical, and unknown-version inputs
